## What this project has delivered (all verified offline)

### The Apple session (MFi) stack

The stock firmware's entire iAP2 session layer was decoded
instruction-by-instruction from the vendor's own V122 image and ported
byte-faithfully into the custom firmware. This is what lets the iPhone
talk to the keyboard as an accessory (not just as a plain USB HID
keyboard). Without it, no phone app can reach the keyboard. The full
decode record with every stock address and byte table:
`keyboards/ck5200/docs/STOCK_DECODE.md`.

Key facts:

- **Attach**: the keyboard sends `FF 55 02 00 EE 10` every 475 ms;
  the iPhone echoes it back; the link starts.
- **Link sync**: `FF 5A` framing, 23-byte sync request with parameters
  (2000 ms retransmit, 500 ms ack, 30 retries, session id 10).
- **Identify**: the iPhone sends `0x1D00`; the keyboard replies with
  sixteen parameters (name, model, serial, versions, protocol string).
- **Auth**: the iPhone sends `0xAA00` (certificate) then `0xAA02`
  (challenge). The keyboard relays both over bit-banged I2C on
  PA13/PA14 to the MFi authentication chip (a licensed Apple chip on
  the board). The chip streams its signed certificate in 128-byte
  chunks and returns the challenge response. The iPhone validates and
  sends `0xAA04` (accepted).
- **Session open**: `0x1D02`, then the raw companion protocol flows on
  USB endpoints `0x03`/`0x83`.

Port files: `keyboards/ck5200/firmware/platform/ch32v20x/iap2.c`,
`iap2_auth.c`, `iap2_ident_data.h` (generated by
`tools/stock_audit/extract_ident.py`, byte-identical to the image).

Harnesses: `tests/iap2_session_test.c` (13 scenarios, every outgoing
packet asserted byte-for-byte against a scripted iPhone) and
`tests/iap2_auth_test.c` (4 scenarios, a waveform-level I2C slave
decoding the bit-bang driver). These harnesses caught five real bugs
during development, all fixed.

### The physical keymap

All 36 electrical crossings were decoded from the stock image (stock
`0x2b1c..0x3010`). The matrix is 6x6: PB row high, read PA0..PA5.
One crossing (row 2, bit 3) is a spare with no key.

Four layers on the QMK dynamic keymap (editable live from the phone
app, persisted in wear-leveled flash at `0x0800F800`):

- **Layer 0**: stock QWERTY base (q w e r t y u i o p / a s d f g h j k
  l / z x c v b n m, Backspace, Enter, Space, Cmd, Ctrl, three consumer
  keys, the Clicks key, the sticky SYM key).
- **Layer 1**: stock SYM values (letters map to their row numbers,
  punctuation elsewhere).
- **Layer 2**: stock cursor-mode arrows, reached by holding the Clicks
  key (`LT(2, KC_J)` — tap is `j`, hold is the arrow layer).
- **Layer 3**: reserved.

Layout test: `tests/test_keymap_layout.py` (pytest, asserts every
crossing of every layer against the decoded table).

### The backlight

TIM1 PWM on PA8/PA9/PA10 (stock `0x306a` init, `0x3010` brightness
formula: `CCR = (0x100 - raw) * 6000 >> 8`, raw byte inverted).
Brightness commands: `03 82 raw` (set and persist),
`02 84` (read). Driver: `firmware/platform/ch32v20x/ck5200_backlight.c`.

Harness: `tests/ck5200_backlight_test.c` (asserts every TIM1 register
value against the decode).

### Consumer keys

The HID report carries a 16-bit consumer field after the 6KRO boot
report (10 bytes total, keeping six-key rollover that stock never
had). One crossing maps to consumer Eject (`0x00B8`), which toggles
the iOS on-screen keyboard. Module: `ck5200_consumer.c`.
Harness: `tests/ck5200_consumer_test.c`.

### The update and restore path

The custom firmware implements the stock A1/A2/A3/A0 update dialect,
so the same protocol flashes custom onto stock (first flash) and
restores stock onto custom (recovery). The staging writer
(`ck5200_staging.c`) writes 256-byte pages to `0x08008A04`, verifies
each, and commits the length word at `0x08008A00` on A3.

Harness: `tests/ck5200_restore_test.c` (pushes the complete real stock
image and the complete real custom image through the real handler and
real staging writer against a mocked flash backend, three full cycles
in both directions, byte-for-byte page equality, plus rejection paths
and injected flash-page failure with recovery).

### The iOS app

`ios/ClicksInspector/` — a SwiftUI app that connects to the keyboard
over Apple's External Accessory framework. It can:

- Discover accessories, open EA sessions, read stock values.
- **Flash custom firmware** (bundled, one tap) from stock or custom.
- **Restore stock firmware** (bundled V122, one tap) from either state.
- **Run a self-test**: identify, read all 144 keys, verify against the
  decoded factory layout, round-trip a write. Per-check pass/fail report.
- **Test keys**: a focused text field where you type on the physical
  keyboard; every character proves the HID path works.
- **Preview layouts**: color-coded grid with readable key names.
- **Edit the keymap**: per-key hex and named presets, durable writes.

Three host-runnable Swift checks pass (protocol, layout/self-test,
stock reads).

### Validation infrastructure

- `tools/preflight_check.sh`: 10 automated pre-flash checks, all pass.
- `tools/verify_history.sh`: builds every commit on main standalone;
  11/11 pass as of this writing.
- `tools/stock_audit/`: the extraction tooling that re-derives every

- `docs/FLASHING.md`: the definitive guide (procedure, risk table,

## Current gaps (honest, no sugar-coating)

### The big one: nothing has run on hardware

The first flash is the first live test. Everything above is offline
verification. The known runtime risks, in order of likelihood:

1. **MFi session stack**: statically faithful but never exercised
   against a real iPhone. The auth chip may need a different I2C
   address or timing. The iPhone's `0xEA00` EA-open message carries
   a parameter we parse shallowly.
2. **Physical key feel**: the debounce is a global 5 ms settle
   (`sym_defer_g`); real keys may ghost or chatter. QMK's per-key
   debounce (`sym_eager_pk`) was swapped out to remove a malloc
   dependency and may need to be revisited.
3. **Backlight**: TIM1 registers are stock-faithful, but the actual
   LED wiring on PA8/PA10 is inferred from the stock decode, never
   confirmed on the board.
4. **USB enumeration**: TinyUSB with stock-topology descriptors.
   Low risk, but the alt-setting-1 EP3 pair has never been exercised
   by a real host.

### The small ones

- **Boot region** (`0x0000..0x2000`): never read, never audited.
  The stock installer lives there. We cannot dump it without physical
  access. Its signature/checksum behavior on a non-vendor image is
  unknown. It may reject our staged image.
- **Full flash backup**: no memory-read command exists in the stock
  protocol. Software-only readback is closed (audited and documented).
- **Settings commands** `0x86`/`0x88`/`0x8a`/`0x8c`/`0x8d`:
  not implemented. The iOS inspector reads them on stock; our firmware
  returns the unsupported-command status rather than lying.
- **Backlight auto-off**: stock has an activity-based on/off state
  machine (the backlight turns off after the configured delay). We
  ported the brightness driver but not this state machine; the
  backlight stays on.
- **Multi-packet link frames**: the session stack parses one USB
  packet at a time. If the iPhone sends a link frame that spans
  multiple 64-byte USB packets, we drop it. Stock had the same
  limitation, so this is stock-faithful but could matter.
- **Per-commit buildability of the `ios/` commits**: the two iOS-only
  commits (`0baba11`, `7c89b90`) are not firmware commits and were
  not build-tested by `verify_history.sh` (it only builds the
  firmware). They compile on Xcode but that is not verified by the
  repo's automated checks.

## Next steps (prioritized)

### Step 0: decide to flash

Rudi owns this decision. The preflight passes, the risk table in
`docs/FLASHING.md` section 3 is the honest summary, and the Mac
restore path is the backup. Read `docs/FLASHING.md` fully before
proceeding.

### Step 1: flash and validate

1. Run `bash keyboards/ck5200/tools/preflight_check.sh` (10/10 pass).
2. Verify the stock keyboard types on the iPhone (Notes app).
3. Flash from the Clicks Inspector app ("Flash bundled custom firmware").
4. After reboot, follow the 10-step post-flash checklist in
   `docs/FLASHING.md` section 6.
5. If any step fails, follow the "what to do if a check fails" table
   in the same section.

### Step 2: debug what fails (if anything)

- **MFi session fails**: check the auth chip address (the driver tries
  `0x22` then `0x20` after 20 failed peeks). Add a third address if
  needed. Check the I2C timing (`auth_bit_delay` in `iap2_auth.c`).
  Capture the phone's `0xEA00` message and extend the parser.
- **Typing fails or ghosts**: switch to per-key debounce, or add a
  debounce-scanner that reads the matrix twice.
- **Backlight dead**: verify PA8/PA9/PA10 are actually the LED pins.
- **USB dead**: this is the only unrecoverable case without physical
  programming. See `docs/RECOVERY.md`.

### Step 3: implement the remaining settings

After the first flash succeeds, add the settings commands that the
iOS inspector reads on stock:

- `0x86` (backlight delay): needs the auto-off state machine.
- `0x88` (battery idle interval): needs a battery/charge source.
- `0x8a`, `0x8c`, `0x8d`: raw configuration reads.

### Step 4: quality-of-life improvements

- Per-key debounce (swap `sym_defer_g` back for `sym_eager_pk` with
  static allocation).
- Multi-packet link frame reassembly.
- The Clicks key (`5,4`) and z-key (`3,8`) configurable behaviors
  (stock `0x11f` and `0x11e` config offsets).
- Keymap editor: import/export, drag-and-drop, more presets.

## Potential future enhancements

1. **HID over iAP2**: the stock firmware may support the iPhone's
   iAP2 HID session (message `0x6800` StartHID). If the iPhone prefers
   iAP2 HID over the USB HID interface for typing, the custom firmware
   would need to implement it. This has not been investigated.
2. **Power/battery reporting**: the stock sends `0xAE00`
   (StartPowerUpdates) and receives `0xAE01` (PowerUpdate). The
   keyboard could report its battery level to the phone.
3. **Boot region dump**: requires physical access (see
   `docs/RECOVERY.md` section "Hardware backup and restore guide").
   A full dump would settle the installer's signature behavior.
4. **Custom keymap profiles**: multiple saved layouts, switchable
   from the app or a keyboard shortcut.
5. **Backlight auto-off**: port the stock's activity-based state
   machine so the backlight turns off after the configured idle delay.
6. **Official app compatibility**: the official Clicks app may reject
   the custom firmware if it checks the firmware version string or
   protocol behavior beyond the identify message. Test and adjust.
7. **The 9981-style "sticky ctrl"**: one-handed modifier chords.
   QMK has one-shot modifiers (`OSM`); they are already in the
   keymap encoding but not bound to any key yet.

## The one thing to remember

This project's value is that it was built from evidence, not guesses.
Every byte in the firmware, every timing constant, every register
write traces back to a specific instruction in the stock image. If you
change something, say why. If you add something, decode it first. If
you are about to flash, run the preflight. If you break something,
revert and diagnose. The keyboard is the only one.
